# Apprentice developer - start here

Welcome. If you are starting out as an apprentice developer, this page is
for you: what the role is about, where to find everything else this
repository has for it, and a pathway for building the skills it asks for,
one step at a time.

## Purpose

A software developer designs, runs and improves software that meets user
needs — writing clean, secure code following a test-driven approach, and
creating code that's open by default and easy for others to reuse. As an
apprentice, you're attending certified training and building that practice
on the job: spending a substantial portion of your time shadowing others,
working alongside developers on code and tests, and following a test-driven
approach so that writing tests becomes a habit rather than an afterthought
from day one. Ask for a code review on everything you write for the first
few months — reviews are how the team teaches, not a test you pass.

## Learning pathway

Work through these roughly in order. Each one is a requirement of this role
level, described plainly, with a way to go deeper by asking an AI tool a
specific question — the answers you get will be shaped around your own
team's codebase, which a generic tutorial never is.

- [ ] **Write, test and document a simple program under direction**

  Design, code, test, correct and document simple programs or scripts under
  the direction of others — the whole small cycle, not just typing the
  code.

  Ask AI: "Walk me through the full cycle of writing a simple program:
  designing it, coding it, testing it, and documenting it, so I don't skip
  a step under time pressure."

- [ ] **Understand why development standards exist**

  Explain the importance of using modern development standards, even though
  applying them under guidance comes at the next level.

  Ask AI: "Explain, for a complete beginner, what 'modern development
  standards' means in software engineering and why teams bother enforcing
  them."

- [ ] **Learn what prototyping is for**

  Explain what prototyping is, and why and when to use it, and start
  understanding how to work in an open, collaborative way — for example, by
  working in a pair with someone more experienced.

  Ask AI: "Explain what a prototype is in software development, why teams
  build one before the real thing, and what pair working actually looks
  like day to day."

- [ ] **Get comfortable helping fix service faults**

  Help with the investigation and fixing of service faults, completing
  defined activities under direction — you are not expected to diagnose a
  fault alone yet, only to help competently once someone more senior has
  pointed you at it.

  Ask AI: "What should someone new to a team do first when they're asked to
  help investigate a service fault, so they're useful rather than in the
  way?"

- [ ] **Build a basic sense of who you're building for**

  Show an awareness or understanding of user experience analysis and its
  principles, and explain the purpose of user stories and why they focus
  on user needs rather than technical convenience.

  Ask AI: "Why do teams write user stories instead of just listing
  technical requirements, and what does a good one actually contain?"

- [ ] **Learn what availability and capacity management actually means**

  Explain availability and capacity management processes — why a service
  needs to stay up, and why "up" isn't enough if it can't handle the load
  it's given.

  Ask AI: "Explain, simply, what 'availability' and 'capacity' mean for an
  online service, and why they're treated as separate concerns."

- [ ] **Start building security awareness**

  Explain information security and the security controls available to
  protect solutions and services, even before you're expected to apply them
  yourself.

  Ask AI: "What are the main categories of security control used to protect
  a software service, explained simply enough for someone new to the
  field?"

You do not need to master all of this before you start. Ask your manager or
whoever you're shadowing which of these your team leans on most, and start
there.
