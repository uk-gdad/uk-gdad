# Test engineer - start here

Welcome. If you are working toward the test engineer level, this page is for
you: what the role expects, where to find everything else this repository has
for it, and a pathway for building the skills it asks for.

## Purpose

A test engineer is responsible for writing, debugging and refactoring test
code — the point where testing becomes a craft you own rather than a set of
steps someone hands you. You will sit close to developers to agree what "well
covered at unit level" actually means for the code in front of you, work with
analysts to make sure acceptance tests reflect real business scenarios rather
than a narrow reading of a ticket, and take on both the functional behaviour
of what you're building and the non-functional properties — performance,
security, resilience — that only show up under pressure. You will also start
coaching testers newer than you, which is its own kind of learning: explaining
something well is one of the fastest ways to find out how well you actually
understand it.

## Learning pathway

Work through these roughly in order. Each one is a requirement of this role
level. Where you want to go deeper than the description here, ask an AI tool a
specific question rather than searching for a generic tutorial — you'll get an
answer shaped around your own codebase, tools and team, which a search result
never will.

- [ ] **Get comfortable reading, writing and fixing test code**

  This is what sets the level apart from the one below it: you are expected to
  write, debug and refactor test code yourself, not just follow a script
  someone else designed. That means treating test code with the same care as
  production code — clear names, no duplication, failures that tell you
  something useful.

  Ask AI: "What separates well-written test code from poorly-written test
  code? Give me examples of common test code smells and how to fix them."

- [ ] **Work out what actually needs testing, and why**

  Work with stakeholders to decide which functional and non-functional
  quality characteristics genuinely add value for this piece of work, agree
  what to test, and analyse the information in front of you — user stories,
  designs, prototypes — to spot where the risk actually sits.

  Ask AI: "Given a feature description I give you, help me identify which
  quality characteristics matter most and where the real risk in testing it
  is likely to be."

- [ ] **Build and adapt a testing approach based on risk**

  Rather than following someone else's plan, you are expected to create or
  adapt a quality testing approach yourself, with some support, and to follow
  and help improve an existing testing strategy over time.

  Ask AI: "Explain how to build a risk-based test approach for a piece of
  work: what questions to ask, and how the answers should change what and how
  much you test."

- [ ] **Design, build and run a fuller range of tests, including exploratory testing**

  Beyond following a script, you are expected to select suitable test types
  and techniques with some support, set up your own test environments, and
  actively try exploratory testing — deliberately unscripted testing driven
  by what you learn as you go — alongside researching new approaches worth
  trying.

  Ask AI: "Explain what exploratory testing is, how it differs from scripted
  testing, and how to structure an exploratory testing session so it stays
  useful rather than aimless."

- [ ] **Use the tools and practices that make testing sustainable at scale**

  Use test engineering frameworks and tools to support your work, follow
  practices like source control and continuous integration and deployment
  pipelines, and create and maintain automated tests with some support —
  including writing and reviewing coded test solutions.

  Ask AI: "Explain how automated tests typically fit into a continuous
  integration and deployment pipeline, and what 'early testing and continuous
  feedback' means in practice."

- [ ] **Take more ownership of defects, dependencies and risk**

  Move from following a defect process to helping build one: critically
  assess dependencies, defects and risks with some support, contribute to
  mitigation and contingency plans, and communicate the impact of defects to
  stakeholders clearly enough that they can make a decision from it.

  Ask AI: "How should a tester weigh up and communicate the risk a defect
  poses, in a way that helps a non-technical stakeholder decide whether to fix
  it now or later?"

- [ ] **Grow into communicating across a wider range of people**

  You'll increasingly host and support discussions within a team that has
  genuine disagreements in it, act as an advocate for your team to people
  outside it, and manage stakeholders who see the same problem differently.

  Ask AI: "Give me a scenario where a developer and a product owner disagree
  about whether a defect needs fixing before release, and suggest how a tester
  might help the discussion reach a decision."

Ask your manager or a more senior colleague which of these your team relies on
most right now, and start there.
