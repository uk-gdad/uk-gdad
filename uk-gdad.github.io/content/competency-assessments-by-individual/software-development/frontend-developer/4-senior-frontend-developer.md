# Frontend developer (Senior frontend developer) - Competency Assessment

## Introduction

This is for you: a chance to rate your own current strengths against the
baseline the UK GDAD Profession Capability Framework sets for this role
level, using the framework's own words for what it covers.

A frontend developer designs, builds and improves website software that meets user needs. A senior frontend developer is an experienced developer who works with minimal support and can influence and mentor others.

Work through the competency matrix below, one skill at a time, then fill in
the overall determination at the end. Treat this as a mirror, not a test —
there's no assessor watching, so being honest with yourself only costs you a
slightly less flattering picture today in exchange for a far more useful one.
Read `## Advisory` before you begin.

## Advisory

This competency assessment is created by AI and is a work in progress for
educational purposes. It is not a validated assessment instrument — it has
not been piloted, normed or checked for adverse impact — and a rating you
give yourself here must never be treated as equivalent to a formal
assessment for a hiring, promotion, pay or performance decision. Use it for
your own reflection, and talk to your manager, a mentor, or your
organisation's people development team about what you find.

## How to use this assessment

**Preparing.** Read `## About this role level` first, so you're rating
yourself against what this level actually expects rather than the level
above or below it. Then think back over recent, real examples of your work —
not how you'd like to have handled something, but what you actually did.

**Rate on evidence, not impression.** For every skill, try to recall a
specific moment that supports the rating you give yourself. If you can't
think of one, that's useful information too — it might mean the rating
should be lower, or just that you haven't had the chance to show this skill
yet, which is worth noting separately.

**Be consistent with yourself.** Try to apply the same standard across every
skill, rather than being generous where you feel confident and harsh where
you feel unsure. Coming back to this after a few days, with fresh examples in
mind, often sharpens a rating more than sitting with it in one go.

**Be kind, and be honest.** This only works if you can look at the result
without flinching. A low rating here is not a verdict on you — it's a
starting point. Everyone doing this role, at every level, has skills they are
still building.

## Rating scale

Every skill in the competency matrix below is rated on the same five-point
scale:

| Value | Rating | Meaning |
| ---: | --- | --- |
| 0 | None | No demonstrated experience of this skill |
| 1 | Beginner | Just starting to learn the skill; requires close supervision |
| 2 | Intermediate | Knows the basics and can perform tasks with some guidance |
| 3 | Advanced | Has a strong grasp of the skill and can work independently |
| 4 | Expert | Demonstrates full mastery and can teach or guide others in the skill |

This is a **proficiency** scale, not a frequency scale. It rates how well someone does the thing, on the evidence in front of you, not how often they do
it or how confident they say they feel about it.

**Worked example — Web performance optimisation.** Someone who mentions
having "looked at page speed once" but cannot describe what they checked or
what changed sits at 0 or 1: there is no evidence of a repeatable skill, only
a vague recollection. Someone who can walk you through diagnosing a slow
page — checking bundle size, image weight, and render-blocking scripts, and
fixing the worst offender — but needed a senior colleague to point them at the
right tooling sits at 2: the basics are there, but someone still needed
guidance to get moving. Someone who describes, unprompted, setting up
performance budgets, instrumenting real-user monitoring, diagnosing a
regression from first principles, and coaching two other developers through
their own performance investigations sits at 3 or 4, depending on whether the
"coaching others" part is a one-off or a habit: the higher of the two marks
mastery that has already started teaching itself outward.

## About this role level

**The role: Frontend developer.** A frontend developer designs, builds and
improves website software that meets user needs. In this role, a person is
responsible for writing clean, accessible code following a progressive
enhancement approach, for creating code that is open by default and easy for
others to reuse, for designing software that meets user needs and creates
meaningful interactions and relationships with users, and for understanding
the three fundamental frontend technologies: HTML, CSS and JavaScript.

**This role level: Senior frontend developer.** A senior frontend developer is
an experienced developer who works with minimal support and can influence and
mentor others. At this role level, a person helps set direction and embed good
practice within teams, makes decisions based on research, plans and leads
development on sets of related stories while working with other disciplines
to understand what needs to be built, has an understanding of the whole
system, and teaches and mentors others.

**Where this sits in the frontend developer ladder**, in order:

1. Apprentice frontend developer
2. Junior frontend developer
3. Frontend developer
4. **Senior frontend developer** — this level
5. Lead frontend developer
6. Head of frontend development

**The skills this level names**, in the framework's order:

- Accessibility
- Communicating information
- Community collaboration
- Leadership and guidance (frontend developer)
- Modern development standards
- Programming and build (frontend developer)
- Prototyping
- Strategic thinking
- Systems integration (frontend developer)
- User focus (frontend developer)
- Web performance optimisation

## Competency matrix

### Skill: Accessibility

**What the framework expects at this level**

A senior frontend developer builds user interfaces that meet a predefined set
of accessibility standards, champions accessibility to internal stakeholders,
offers design feedback that mitigates the risk of failing accessibility
testing, and recommends the best tools and methods for accessibility testing.

**Baseline for this role level**

Baseline: 3 — Advanced. This level's own wording moves beyond building to
standard — it asks someone to champion accessibility outward and to give
design feedback that pre-empts test failures, which needs independent
judgement a less experienced developer would not yet be trusted with.

**Behavioural indicators**

- 0 — None: Cannot explain what makes an interface accessible or point to
  any accessibility standard, and code produced fails basic checks such as
  keyboard operability or colour contrast.
- 1 — Beginner: Knows a few accessibility rules of thumb (alt text, heading
  order) but applies them inconsistently, and needs a reviewer to catch most
  issues before code ships.
- 2 — Intermediate: Consistently meets a named accessibility standard on
  their own code with some guidance, and can explain why a given fix is
  needed when asked, but does not yet raise accessibility concerns
  unprompted.
- 3 — Advanced: Reviews other people's interface designs and flags
  accessibility risks before they reach testing, recommends specific tools
  or testing methods to the team, and can explain accessibility trade-offs
  to a non-technical stakeholder.
- 4 — Expert: Has changed how a team or organisation approaches
  accessibility — for example, introducing a testing process, a component
  library pattern, or a review gate — and is sought out by other teams for
  accessibility judgement calls.

**Evidence to gather**

- Think about how you'd review a short interface mock-up or live component
  and identify accessibility issues on sight, then explain how you would
  fix each one.
- Ask for an example of a time you raised an accessibility concern with a
  designer or product manager before a feature shipped, and what happened.
- Look back at a pull request or code sample for accessibility practice: semantic
  markup, keyboard operability, ARIA use only where native semantics fall
  short.
- Ask a referee what tools or testing methods this person has recommended to
  a team, and whether the recommendation stuck.

### Skill: Communicating information

**What the framework expects at this level**

A senior frontend developer works collaboratively and builds relationships
with others, identifies issues through Agile "health checks" and works with
others to address them, manages stakeholder expectations, communicates both
proactively and reactively as the situation needs, and hosts or moderates
difficult discussions within the team or with senior stakeholders.

**Baseline for this role level**

Baseline: 3 — Advanced. Hosting or moderating a difficult discussion with a
senior stakeholder is not a supervised task — it requires someone who can
already read a room and manage disagreement independently, which places the
baseline above "can perform tasks with some guidance".

**Behavioural indicators**

- 0 — None: Communicates only when directly asked, and status updates from
  this person leave a listener unsure what is actually happening on the
  work.
- 1 — Beginner: Gives clear updates on their own work when prompted, but
  does not yet raise emerging problems proactively or take part in
  resolving team-level friction.
- 2 — Intermediate: Proactively flags a risk or a blocker to the right
  person, and can explain a technical decision to someone outside the
  immediate team with some coaching on how to pitch it.
- 3 — Advanced: Runs or actively contributes to an Agile health check, turns
  what it surfaces into concrete follow-up actions with others, and can
  manage a stakeholder's expectations when a delivery date slips.
- 4 — Expert: Has personally facilitated a genuinely difficult conversation
  — a disagreement between senior stakeholders, a team in conflict, an
  escalation — to a resolution that stuck, and other people ask them to
  handle that kind of conversation again.

**Evidence to gather**

- Ask for a specific example of a difficult conversation you hosted or
  moderated, what made it difficult, and what the outcome was.
- Reflect on a recent time you explaining a technical constraint to a
  non-technical stakeholder role-played by the panel, and note whether
  expectations are actually managed rather than just restated.
- If you can, ask a manager, mentor or colleague to describe how this person behaves in an Agile retrospective
  or health check when the feedback in the room is uncomfortable.
- Look back at any written stakeholder communication you can share
  (with sensitive details removed) for clarity and tone.

### Skill: Community collaboration

**What the framework expects at this level**

A senior frontend developer works collaboratively in a group, actively
networking with others, adapts feedback so that it is effective and lasting,
uses their specialism to identify problems or issues in the team dynamic and
rectify them, and helps a team respond well to what Agile health checks
surface.

**Baseline for this role level**

Baseline: 2 — Intermediate. The framework's own wording here is about
networking and adapting feedback within a group rather than about setting
direction or exercising independent authority, so — unlike this level's more
directive skills — the baseline sits at "can perform with some guidance"
rather than fully independent practice.

**Behavioural indicators**

- 0 — None: Works in isolation, does not engage with a wider community of
  practice, and feedback given to others tends to land badly or get
  ignored.
- 1 — Beginner: Takes part when a community activity is organised for them —
  a guild, a demo, a show-and-tell — but does not initiate contact or adapt
  their feedback to someone receiving it.
- 2 — Intermediate: Actively participates in a community of practice or
  cross-team forum, and adjusts how they give feedback depending on who is
  receiving it, with some coaching on the harder cases.
- 3 — Advanced: Uses their own technical specialism to spot a team dynamic
  problem — for example, one person's work always needing rework — and
  raises it constructively before it escalates.
- 4 — Expert: Is a recognised connector across teams or communities of
  practice, routinely brings back useful practice from outside their own
  team, and is asked by other teams to help diagnose a dynamic that is not
  working.

**Evidence to gather**

- Ask what communities of practice, guilds, or cross-team forums you have taken part in, and what you personally contributed rather
  than attended.
- Ask for an example of feedback you gave that you had to adapt for the
  person receiving it, and what you changed.
- Ask a referee whether this person has identified and helped fix a team
  dynamic issue, and how.
- Reflect on a recent time you in a small group exercise and note whether you
  draw quieter contributors in or dominate the room.

### Skill: Leadership and guidance (frontend developer)

**What the framework expects at this level**

A senior frontend developer makes decisions characterised by medium levels of
risk and complexity, can recommend decisions as risk and complexity increase
beyond that, and contributes to best practice guidelines.

**Baseline for this role level**

Baseline: 3 — Advanced. Making medium-risk decisions unsupervised, and having
a credible voice on decisions above that level, is exactly what "works
independently" means in practice for this skill, and the ladder reserves
owning the highest-risk decisions outright for the lead and head of levels
above.

**Behavioural indicators**

- 0 — None: Avoids making decisions without explicit sign-off, even ones
  with limited consequence, and has no visible input into any team practice
  or guideline.
- 1 — Beginner: Makes small, low-risk decisions alone, but escalates
  anything with real trade-offs rather than reasoning through it, even with
  support available.
- 2 — Intermediate: Makes medium-complexity decisions with a colleague to
  check their reasoning, and contributes an idea or a comment when a team's
  best practice guidelines are being discussed.
- 3 — Advanced: Makes medium-risk, medium-complexity decisions alone and
  stands behind the reasoning, and puts forward a considered recommendation
  when a higher-risk decision is being made by someone more senior.
- 4 — Expert: Owns high-risk, high-complexity decisions outright, and has
  authored or substantially reshaped a best practice guideline that other
  developers now follow.

**Evidence to gather**

- Walk through a real decision you made recently — what the
  options were, what you chose, and why — and probe how you weighed the
  risk.
- Ask for an example of a higher-risk decision you were not the final
  owner of, but where your recommendation was sought and used.
- Ask to see a best practice guideline, coding standard, or architecture
  decision record you contributed to, and what your specific contribution
  was.
- If you can, ask a manager, mentor or colleague to describe a decision this person made under some
  uncertainty, and how it turned out.

### Skill: Modern development standards

**What the framework expects at this level**

A senior frontend developer applies modern development standards, and
supports other people in applying them too.

**Baseline for this role level**

Baseline: 3 — Advanced. Applying current standards independently is table
stakes for a senior developer; the second half of this skill's own wording —
supporting others in applying them — is a mentoring behaviour this level is
explicitly accountable for, so the baseline sits at independent practice
plus some visible support to others, not yet full ownership of a team's
standards.

**Behavioural indicators**

- 0 — None: Code and practice show no awareness of current standards for
  the stack in use — for example, no automated testing, no linting, no
  version control discipline.
- 1 — Beginner: Follows modern standards when told exactly what they are,
  but does not yet apply them without a checklist or a reviewer's prompt.
- 2 — Intermediate: Applies modern development standards to their own work
  reliably, but has not yet helped anyone else adopt them.
- 3 — Advanced: Applies modern standards independently and has visibly
  helped at least one other developer adopt a standard they were not
  already using — through review comments, pairing, or a short
  walkthrough.
- 4 — Expert: Has introduced or substantially updated a team's development
  standards — for example, a linting configuration, a testing approach, a
  build tool — and the team has adopted it because they set the example.

**Evidence to gather**

- Look back at a recent code sample or pull request for current standards: test
  coverage, tooling configuration, dependency hygiene.
- Ask for an example of helping a colleague adopt a standard or a tool you
  were not using, and what you actually did to help.
- Ask what changed most recently in the team's development standards, and
  what part you played in that change.
- Ask a referee whether this person's own practice is one other developers
  learn from.

### Skill: Programming and build (frontend developer)

**What the framework expects at this level**

A senior frontend developer collaborates with others when necessary to review
specifications, and uses the agreed specifications to build, test and
document user interfaces of medium to high complexity, using the right
standards and tools.

**Baseline for this role level**

Baseline: 3 — Advanced. "Medium to high complexity" work, built, tested and
documented largely unsupervised, is a direct restatement of independent
practice at a strong level — the natural centre of the scale for the core
technical skill of this role.

**Behavioural indicators**

- 0 — None: Cannot take a specification and produce working, tested code
  from it without extensive step-by-step direction.
- 1 — Beginner: Builds simple interfaces from a clear specification with
  close review, but struggles once requirements are ambiguous or the
  interface is more than a single component.
- 2 — Intermediate: Builds, tests and documents interfaces of moderate
  complexity from a specification with some guidance on approach, and asks
  sensible clarifying questions when the specification is incomplete.
- 3 — Advanced: Builds, tests and documents interfaces of medium to high
  complexity independently, chooses the right tools and standards for the
  job without being told, and reviews a specification critically before
  starting.
- 4 — Expert: Routinely takes on the most complex interface work in the
  team, is trusted to interpret an incomplete specification correctly, and
  others come to them when a build is stuck.

**Evidence to gather**

- Set a realistic build task from a short, deliberately incomplete
  specification, and observe what questions you asks before
  starting.
- Look back at a portfolio or code sample of medium-to-high complexity work,
  including its tests and documentation, not just the interface itself.
- Think about how you'd describe the most complex interface you have built
  recently, what made it complex, and how you tested it.
- If you can, ask a manager, mentor or colleague to describe the hardest build task this person has owned,
  and how it went.

### Skill: Prototyping

**What the framework expects at this level**

A senior frontend developer approaches prototyping as a team activity,
actively soliciting prototypes and testing them with others, establishes
design patterns and iterates them, and uses a variety of prototyping methods,
choosing the most appropriate one for the situation.

**Baseline for this role level**

Baseline: 3 — Advanced. Establishing design patterns and choosing between
prototyping methods, rather than just executing a chosen method, is
independent judgement about how the team should work — squarely an Advanced
behaviour at this level.

**Behavioural indicators**

- 0 — None: Has not built or tested a prototype, or treats prototyping as
  something only a designer does.
- 1 — Beginner: Can build a simple prototype when given a clear method to
  follow, but does not choose the method or involve others in testing it.
- 2 — Intermediate: Builds prototypes using a method the team already uses,
  and tests them with colleagues, with some guidance on which method suits
  which problem.
- 3 — Advanced: Chooses the most appropriate prototyping method for a given
  problem from more than one they know well, actively solicits prototypes
  from others rather than only producing their own, and has established a
  design pattern the team has reused.
- 4 — Expert: Has built and iterated a design pattern that has become a
  standard part of the team's or organisation's component library, and
  coaches others on choosing between prototyping methods.

**Evidence to gather**

- Think about how you'd describe two different problems you have
  prototyped and why you chose different methods for each.
- Ask for an example of a design pattern you established, and how it
  changed after being tested with others.
- Look back at any prototype artefacts you can share, and ask who was
  involved in testing you.
- Ask a referee whether this person actively seeks out prototypes from
  colleagues, or mainly produces your own.

### Skill: Strategic thinking

**What the framework expects at this level**

A senior frontend developer defines strategies and policies, provides
guidance to others on working in the strategic context, evaluates current
strategies to ensure business requirements are being met, and looks for ways
to exceed them where possible.

**Baseline for this role level**

Baseline: 3 — Advanced. Defining a strategy or policy and guiding others
through it is a step up from simply following one, and fits an experienced
developer helping set direction for a team — but authoring strategy across an
entire organisation is lead or head of territory, so the baseline stops short
of Expert.

**Behavioural indicators**

- 0 — None: Works to whatever is asked without engaging with why it matters
  to the wider goal, and cannot describe how their work connects to a team
  or business strategy.
- 1 — Beginner: Can repeat a strategy or policy that already exists, but
  has not helped shape one or spotted where it is falling short.
- 2 — Intermediate: Follows an existing strategy and, with some prompting,
  can identify a case where day-to-day work is not meeting what it asks
  for.
- 3 — Advanced: Has helped define or refine a team-level strategy or
  policy, guides colleagues on how to work within it, and has evaluated
  whether it is meeting its business requirements with a concrete example
  of a change made as a result.
- 4 — Expert: Sets strategic direction that other teams, not just their
  own, work within, and is someone others come to for guidance on
  aligning day-to-day decisions with a longer-term direction.

**Evidence to gather**

- Ask for an example of a team strategy or policy this person helped
  define, and what shape it took before and after your involvement.
- Ask how you evaluate whether a current approach is actually meeting the
  business need it was set up for, and for a concrete example.
- Observe how you connects a technical decision to a wider goal
  when explaining a piece of work.
- Ask a referee whether other people go to this person for guidance on
  strategic direction, or only for hands-on technical help.

### Skill: Systems integration (frontend developer)

**What the framework expects at this level**

A senior frontend developer defines the static assets build, co-ordinates all
aspects of the integration and takes responsibility for the tests around the
user interface, and configures the part of the system that uses the network,
testing that it works as expected.

**Baseline for this role level**

Baseline: 3 — Advanced. Defining a build and taking responsibility for
integration testing is ownership of a whole slice of the system, which needs
independent, unsupervised competence — the level's own "understanding of the
whole system" accountability points the same way.

**Behavioural indicators**

- 0 — None: Cannot describe how their interface work fits into the wider
  system's build or network layer, and has not configured or tested an
  integration point.
- 1 — Beginner: Can follow an existing static assets build and integration
  set-up, but needs step-by-step help to change or troubleshoot it.
- 2 — Intermediate: Makes small changes to a build or network
  configuration with some guidance, and can run existing integration tests,
  though not yet design new ones unassisted.
- 3 — Advanced: Defines or substantially owns the static assets build for a
  project, takes responsibility for the tests around the user interface,
  and configures and verifies the network-facing part of the system
  independently.
- 4 — Expert: Has designed an integration or build approach later adopted
  by more than one team, and is someone others ask when an integration
  problem cannot be explained by anyone else.

**Evidence to gather**

- Think about how you'd walk through how you set up or would set up a
  static assets build for a real project, and what trade-offs you
  considered.
- Ask for an example of an integration test you designed, not just ran,
  and what it caught.
- Look back at a build or deployment configuration you have authored, if
  one can be shared.
- If you can, ask a manager, mentor or colleague to describe a network or integration issue this person
  diagnosed and fixed.

### Skill: User focus (frontend developer)

**What the framework expects at this level**

A senior frontend developer collaborates with user researchers and
interaction designers to represent user needs internally, explains the
difference between user needs and the desires of individual users, champions
user research so that it considers all users, effectively prioritises and
defines approaches to understanding the user story and guides others to do
so, and recommends the best tools and methods to use.

**Baseline for this role level**

Baseline: 3 — Advanced. Guiding other people through prioritising user
research, and championing coverage of all users rather than the loudest
voices, is a step beyond representing user needs oneself — it is this level's
mentoring accountability applied to user focus specifically.

**Behavioural indicators**

- 0 — None: Builds to a specification without reference to who will use it
  or why, and cannot distinguish a user need from a stakeholder's personal
  preference.
- 1 — Beginner: Can repeat what user research has found when asked, but
  does not act on it unprompted or challenge a requirement that conflicts
  with it.
- 2 — Intermediate: Refers to user research when making interface
  decisions, and can explain the difference between a user need and one
  user's request, with some support from a researcher or designer.
- 3 — Advanced: Actively champions research coverage of under-represented
  users, guides a colleague through prioritising which user needs to
  address first, and recommends specific research tools or methods to the
  team.
- 4 — Expert: Has changed how the team gathers or prioritises user
  evidence — for example, introducing a new research method or a
  prioritisation framework — and is sought out across the team for
  judgement on user needs.

**Evidence to gather**

- Ask for an example of a time user research changed a technical decision
  you had already started building.
- Ask how you would prioritise between two conflicting pieces of user
  feedback, one from a small vocal group and one from broader but quieter
  research.
- Reflect on a recent time you explaining, to a colleague role-played by the
  panel, the difference between a user need and a stated user desire.
- Ask a referee whether this person has coached anyone else on
  understanding or prioritising user needs.

### Skill: Web performance optimisation

**What the framework expects at this level**

A senior frontend developer identifies and resolves web performance issues,
collects data to monitor and resolve them, and guides others on the best web
performance optimisation software and methods to use.

**Baseline for this role level**

Baseline: 3 — Advanced. Diagnosing and fixing performance issues from
collected data, unsupervised, and then guiding other people on tooling and
method, matches this level's independent-plus-mentoring profile — the same
shape as the worked example in `## Rating scale` above.

**Behavioural indicators**

- 0 — None: Has no method for finding out why a page is slow beyond a
  general impression, and has not used a performance measurement tool.
- 1 — Beginner: Can run a performance tool when told to and read its
  headline score, but cannot yet turn the output into a fix without help.
- 2 — Intermediate: Diagnoses a common performance issue — a large bundle,
  an unoptimised image, a render-blocking script — and fixes it with some
  guidance on prioritisation.
- 3 — Advanced: Independently diagnoses and resolves web performance
  issues using collected data such as real-user or lab metrics, and has
  recommended a specific tool or method that a colleague then adopted.
- 4 — Expert: Has set up ongoing performance monitoring or a performance
  budget that the team now works to, and is someone the team asks first
  when a performance regression cannot be explained.

**Evidence to gather**

- Give yourself a real or simulated slow page and try to talk
  through how you would diagnose and prioritise fixes.
- Ask for an example of a performance issue you resolved, including what
  data you used to confirm the fix worked.
- Ask what performance monitoring or budget approach you have set up or
  worked within, and what it caught.
- Ask a referee whether this person's performance recommendations have
  been adopted by the wider team.
