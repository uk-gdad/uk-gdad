# Software developer (Apprentice developer) - Competency Assessment

## Introduction

This is for you: a chance to rate your own current strengths against the
baseline the UK GDAD Profession Capability Framework sets for this role
level, using the framework's own words for what it covers.

A software developer designs, runs and improves software that meets user needs. An apprentice developer attends certified training and develops skills on the job.

Work through the competency matrix below, one skill at a time, then fill in
the overall determination at the end. Treat this as a mirror, not a test —
there's no assessor watching, so being honest with yourself only costs you a
slightly less flattering picture today in exchange for a far more useful one.
Read `## Advisory` before you begin.

## Advisory

This competency assessment is created by AI and is a work in progress for
educational purposes. It is not a validated assessment instrument — it has
not been piloted, normed or checked for adverse impact — and a rating you
give yourself here must never be treated as equivalent to a formal
assessment for a hiring, promotion, pay or performance decision. Use it for
your own reflection, and talk to your manager, a mentor, or your
organisation's people development team about what you find.

## How to use this assessment

**Preparing.** Read `## About this role level` first, so you're rating
yourself against what this level actually expects rather than the level
above or below it. Then think back over recent, real examples of your work —
not how you'd like to have handled something, but what you actually did.

**Rate on evidence, not impression.** For every skill, try to recall a
specific moment that supports the rating you give yourself. If you can't
think of one, that's useful information too — it might mean the rating
should be lower, or just that you haven't had the chance to show this skill
yet, which is worth noting separately.

**Be consistent with yourself.** Try to apply the same standard across every
skill, rather than being generous where you feel confident and harsh where
you feel unsure. Coming back to this after a few days, with fresh examples in
mind, often sharpens a rating more than sitting with it in one go.

**Be kind, and be honest.** This only works if you can look at the result
without flinching. A low rating here is not a verdict on you — it's a
starting point. Everyone doing this role, at every level, has skills they are
still building.

## Rating scale

Every skill in the competency matrix is rated on the same five-point scale.
This is a **proficiency** scale: it rates how well someone does the thing,
on the evidence available, not how often they do it or how they feel about
it.

| Value | Rating | Meaning |
| ---: | --- | --- |
| 0 | None | No demonstrated experience of this skill |
| 1 | Beginner | Just starting to learn the skill; requires close supervision |
| 2 | Intermediate | Knows the basics and can perform tasks with some guidance |
| 3 | Advanced | Has a strong grasp of the skill and can work independently |
| 4 | Expert | Demonstrates full mastery and can teach or guide others in the skill |

**Worked example**, using the skill Programming and build (software
engineering), which this role level names:

- A rating of **0 — None** looks like: someone has never written a line of
  code that ran, in an interview task or otherwise, and cannot describe what
  a test is.
- A rating of **1 — Beginner** looks like: given a simple, well-specified
  task and someone sitting alongside them, someone can write a short
  script or function that does roughly the right thing, though it needs
  correction, and they can explain in plain terms what the code they wrote is
  meant to do.
- A rating of **2 — Intermediate** looks like: someone can write, test and
  correct a simple program with some guidance and occasional check-ins,
  rather than continuous supervision, and can document what it does clearly
  enough for someone else to read.

An apprentice developer's evidence will usually sit at the 0–1 end of this
scale for most skills — that reflects where the framework sets the bar for
this level, not someone weak in this.

## About this role level

**The role: Software developer.** A software developer designs, runs and
improves software that meets user needs. In this role, a person is
responsible for writing clean, secure code following a test-driven approach,
and for creating code that is open by default and easy for others to reuse.

**This level: Apprentice developer.** An apprentice developer attends
certified training and develops skills on the job. At this role level, a
person will:

- spend a substantial portion of their time shadowing others
- work with other developers to write code and tests
- build their knowledge
- follow a test-driven approach
- write code that is automatically tested

**Where this sits in the role's ladder.** The software developer role has
nine published levels, run in order from entry point to most senior:

1. **Apprentice developer — this level, the entry point of the ladder**
2. Junior developer
3. Developer
4. Senior developer
5. Senior developer (management)
6. Lead developer
7. Lead developer (management)
8. Principal developer
9. Principal developer (management)

An apprentice developer sits at the very bottom of this ladder. Every
expectation the framework sets for this level is about learning under close
supervision, not about independent delivery — that shapes every baseline
below.

**The skills this level names**, in the framework's order:

- Availability and capacity management
- Information security
- Modern development standards
- Programming and build (software engineering)
- Prototyping
- Service support
- User focus

## Competency matrix

### Skill: Availability and capacity management

**What the framework expects at this level**

The framework asks an apprentice developer to be able to explain
availability and capacity management processes — the ways a team keeps a
service running and makes sure it has enough capacity to meet demand. It does
not ask the apprentice to run these processes themselves.

**Baseline for this role level**

Baseline: 1 — Beginner. This level's whole accountability set is about
attending training, shadowing others and building knowledge, and the skill's
own wording asks only that the apprentice can explain the processes in plain
terms — a beginner-level, knowledge-based expectation that requires close
supervision whenever the processes matter in real work, not independent
practice of them.

**Behavioural indicators**

- 0 — None: cannot say what availability or capacity mean in a service
  context, or confuses them with something unrelated, such as security.
- 1 — Beginner: can explain, in their own words and with prompting, that
  availability is about keeping a service up and capacity is about it coping
  with demand, and can point to an example they have seen mentioned by the
  team, even if they could not yet act on it themselves.
- 2 — Intermediate: can explain the processes unprompted and connect them to
  a real incident or change they shadowed, describing roughly what the team
  did and why.
- 3 — Advanced: can describe how availability and capacity management fit
  into the wider service lifecycle and can spot, in a scenario, a change that
  would put either at risk.
- 4 — Expert: can design or improve an availability or capacity management
  process for a service and coach other developers through applying it.

**Evidence to gather**

- Ask a structured interview question such as: "Tell me about a time you saw
  a service go down, or nearly run out of capacity. What happened, and what
  did the team do?"
- During a shadowing or pairing session, ask the apprentice to describe, in
  your own words, what you just watched a colleague do to check a service's
  health.
- Look back at any training log or portfolio entry from the apprenticeship
  programme that covers this topic.

### Skill: Information security

**What the framework expects at this level**

The framework asks an apprentice developer to be able to explain information
security and the security controls available to protect solutions and
services — again, a knowledge-based expectation rather than a requirement to
apply controls independently.

**Baseline for this role level**

Baseline: 1 — Beginner. The framework's own wording is "explain", and this
level's accountabilities have the apprentice working with other developers
and following a test-driven approach under supervision rather than making
independent security decisions, so a beginner-level ability to explain the
basics, with close supervision on anything security-critical, is the fair
baseline.

**Behavioural indicators**

- 0 — None: cannot name a single security control, or treats security as
  someone else's job entirely with nothing to say about it.
- 1 — Beginner: can name one or two basic controls they have heard of, such
  as not committing a password into code, and can explain in simple terms why
  that matters, though they need prompting to go further.
- 2 — Intermediate: can explain several controls unprompted and describe, in
  general terms, what each protects against, drawing on examples they have
  shadowed or read about during training.
- 3 — Advanced: can spot an insecure pattern in a short piece of code shown to
  them and suggest a fix, and can explain the trade-off the fix involves.
- 4 — Expert: can review a design or a piece of code for security issues
  unprompted, and can coach other developers on secure coding practice.

**Evidence to gather**

- Give the apprentice a short, deliberately insecure snippet of code — for
  example, one that stores a secret in plain text — and try to spot
  anything that concerns you.
- Ask a structured interview question such as: "What is one thing you would
  never do in code you were writing, and why?"
- Look back at any security-related module from the apprenticeship's certified
  training and try to summarise what it covered.

### Skill: Modern development standards

**What the framework expects at this level**

The framework asks an apprentice developer to be able to explain the
importance of using modern development standards — why teams follow shared
conventions and up-to-date practice, rather than the standards themselves in
detail.

**Baseline for this role level**

Baseline: 1 — Beginner. This is the thinnest of this level's skill
expectations — an awareness of *why* standards matter, not fluency in any
particular one — and it sits alongside a level whose defining accountability
is "build your knowledge", so a beginner's ability to give a plain-language
reason, formed through training and shadowing, is the right baseline rather
than none at all.

**Behavioural indicators**

- 0 — None: has no view on why a team would follow shared coding standards,
  or says it does not matter as long as the code runs.
- 1 — Beginner: can give one plain reason modern development standards
  matter — for example, "so other people can read my code" — when asked
  directly.
- 2 — Intermediate: can give more than one reason unprompted, such as
  consistency, easier reviews and fewer mistakes, and can connect this to
  something they have seen on their own training or shadowing.
- 3 — Advanced: can explain why a particular standard exists by pointing to a
  problem it prevents, and follows the team's standards consistently in their
  own work without being reminded.
- 4 — Expert: helps set or update a team's development standards and explains
  the reasoning to others in a way that changes how they work.

**Evidence to gather**

- Ask a structured interview question such as: "Why do you think a team
  agrees on a shared way of writing code, rather than everyone doing your own thing?"
- During a pairing or shadowing session, note whether the apprentice asks
  about, or follows, the team's existing conventions once shown you.
- Look back at any relevant training log entry that covers coding standards or
  conventions.

### Skill: Programming and build (software engineering)

**What the framework expects at this level**

The framework asks an apprentice developer to design, code, test, correct and
document simple programs or scripts under the direction of others — the most
hands-on of this level's skills, and the one closest to the role's own core
duty of writing clean, secure, tested code.

**Baseline for this role level**

Baseline: 1 — Beginner. The framework's own wording caps this at "simple
programs or scripts under the direction of others", which matches this
level's accountabilities of working with other developers to write code and
tests and following a test-driven approach while still building knowledge —
a beginner who needs direction, not someone working independently.

**Behavioural indicators**

- 0 — None: cannot produce a small working program or script, with or
  without direction, and has no experience of writing an automated test.
- 1 — Beginner: with close direction — a task broken down for them and
  someone available to check in with — can write a short, simple script or
  function, add a basic test for it, and fix an obvious mistake once it is
  pointed out.
- 2 — Intermediate: given a simple, well-defined task, can design, code and
  test it with some guidance rather than step-by-step direction, and can
  write short, clear documentation of what it does.
- 3 — Advanced: can independently design, build, test and document a small
  program or script from a plain description of what it needs to do, and can
  correct their own mistakes without help.
- 4 — Expert: can design and build more complex software independently, and
  can review and improve other people's programs or scripts.

**Evidence to gather**

- Set a supervised coding exercise: a small, well-specified task with an
  assessor or mentor on hand, and observe how much direction the apprentice
  needs to complete it.
- Look back at a work sample from a pairing session — code the apprentice wrote
  alongside a colleague — and the automated test that goes with it.
- Think about how you'd walk through, in a structured interview, how you went about a
  recent piece of code from your training: what you built, how you tested
  it, and what you got stuck on.
- Review the apprenticeship programme's portfolio or training log for
  completed coding exercises and the feedback given on you.

### Skill: Prototyping

**What the framework expects at this level**

The framework asks an apprentice developer to be able to explain what
prototyping is, and why and when to use it, and to understand how to work in
an open and collaborative environment, such as by pair working.

**Baseline for this role level**

Baseline: 1 — Beginner. Both parts of this skill are framed as
"explain" and "understand" rather than "do", which fits an apprentice who is
still building knowledge and working alongside other developers rather than
running their own prototyping work — a beginner's grasp, gained through
shadowing and training, is the fair baseline.

**Behavioural indicators**

- 0 — None: cannot say what a prototype is, or has never taken part in pair
  working of any kind.
- 1 — Beginner: can give a simple definition of a prototype — for example, a
  rough version built to try an idea out before building it properly — and
  has taken part in at least one pair working session, even if they mostly
  watched.
- 2 — Intermediate: can explain why a team would build a prototype rather
  than going straight to the finished thing, and can describe how they
  contributed something, however small, during a pairing session.
- 3 — Advanced: can help build a simple prototype themselves to test an idea,
  and works comfortably and openly alongside another developer without
  needing to be drawn in.
- 4 — Expert: leads a prototyping exercise, choosing what to build and what
  to leave out to answer the question at hand, and actively draws quieter
  collaborators into the work.

**Evidence to gather**

- Ask a structured interview question such as: "What is a prototype, and why
  might a team build one before writing the real thing?"
- Observe a pair working session and note how actively the apprentice
  participates, rather than only watching.
- Think about how you'd describe a time, in training or on the job, when something was
  tried out roughly before being built properly.

### Skill: Service support

**What the framework expects at this level**

The framework asks an apprentice developer to help with the investigation and
fixing of service faults, completing defined activities under direction —
supporting the work rather than owning it.

**Baseline for this role level**

Baseline: 1 — Beginner. "Help with" and "defined activities under direction"
describe someone assisting a more experienced colleague on a fault, which
matches this level's expectation of shadowing others and building knowledge —
a beginner able to carry out a small, clearly defined task once told what to
do, not someone who can triage a fault alone.

**Behavioural indicators**

- 0 — None: has never taken part in investigating or fixing a service fault,
  even alongside someone else.
- 1 — Beginner: given a clearly defined, small task by someone more
  experienced — for example, "check whether this error appears in the logs"
  — can carry it out and report back what they found.
- 2 — Intermediate: can carry out more than one defined activity during a
  single fault investigation with some guidance, and can summarise what was
  found in their own words to someone leading it.
- 3 — Advanced: can help investigate a fault with only light guidance,
  suggesting a next step rather than only carrying out one they are given.
- 4 — Expert: can lead the investigation and fixing of a service fault, and
  direct others in defined activities during it.

**Evidence to gather**

- Ask the apprentice to describe a service fault you have helped
  investigate, what activity you were given, and what the outcome was.
- Observe you shadowing or assisting on a live or simulated fault
  investigation, and note how much direction you need to complete a defined
  task.
- Look back at any incident or fault-related entry in your training log or
  portfolio.

### Skill: User focus

**What the framework expects at this level**

The framework asks an apprentice developer to show an awareness or
understanding of user experience analysis and its principles, and to explain
the purpose of user stories and the focus on user needs.

**Baseline for this role level**

Baseline: 1 — Beginner. Both parts of this skill ask for awareness or an
ability to explain, not for the apprentice to carry out user research or
write user stories themselves, which matches a level built around building
knowledge under supervision rather than independent delivery — a beginner's
grasp is the fair baseline.

**Behavioural indicators**

- 0 — None: cannot say what a user story is, or shows no awareness that
  software is built to meet a user's needs rather than for its own sake.
- 1 — Beginner: can explain, when asked, that a user story describes what a
  user needs and why, and can point to a user story from their own team's
  work as an example.
- 2 — Intermediate: can explain unprompted why a team writes user stories
  rather than just a list of technical tasks, and can describe, in general
  terms, what user experience analysis involves.
- 3 — Advanced: can read a user story and explain, in their own words, what
  user need it is trying to meet, and can spot when a piece of work has
  drifted away from that need.
- 4 — Expert: contributes to writing or refining user stories themselves, and
  helps other developers keep user needs in view during their own work.

**Evidence to gather**

- Ask a structured interview question such as: "What is a user story, and
  why do you think a team writes one before building something?"
- Show the apprentice a short user story from real or sample work and try to explain, in your own words, what user need it describes.
- During a pairing or shadowing session, note whether the apprentice refers
  to the user the work is for, once it has been pointed out to you.
