# Major incident manager - upskill resources

This page focuses on learning and growth resources for the work role of major incident manager.

- The resources include links to online courses, blogs, research articles, videos, and books.

- These help with job upskilling, work training, professional development, and career advancement.

- These are intended to be good starting points, not a comprehensive catalogue.

At this role level you manage significant outages and crises and report issues to problem management, working closely with workplace services, infrastructure, applications operators and communication managers. In some departments you may also be head of service. The resources below emphasise incident command, communication under pressure, runbook and continuity discipline, and the cross-team coordination that determines how a major incident goes.

We welcome constructive feedback to improve this page and these lists.

- GitHub issues and/or pull requests are welcome.

- [Advanced Negotiation and Conflict Resolution for Leaders](https://www.coursera.org/learn/advanced-negotiation-and-conflict-resolution-for-leaders): Multi-party dynamics and systematic influence, which is what commanding a crisis with many stakeholders actually requires.

- [Advanced ITSM with ServiceNow: Optimizing IT Operations](https://www.coursera.org/learn/advanced-itsm-with-servicenow-optimizing-it-operations): Incident, problem, change and configuration management, at the level where you hold the whole picture.

## Research articles

- [Failures and Fixes: A Study of Software System Incident Response](https://arxiv.org/pdf/2008.11192): An empirical study of how incident response actually happens, including where coordination breaks down.

- [Interorganizational coordination during emergencies and crises](https://www.sciencedirect.com/science/article/pii/S2212420925001347): Coordination across organisational boundaries in crises, which is the hard part of a major incident.

- [Incident response: A structured model from detection to containment and recovery](https://www.researchgate.net/publication/385382098_Incident_response_A_structured_model_from_detection_to_containment_and_recovery): A phase model, useful for auditing your own process for missing steps.

- [Cyber Incident Response and Planning: A Flexible Approach](https://www.sciencedirect.com/science/article/abs/pii/S1361372321000099): An incident response maturity model developed against practice requirements.

- [Effective Communication as A Pillar of Cybersecurity: Managing Incidents and Crises in the Digital Era](https://www.researchgate.net/publication/393291345_Effective_Communication_as_A_Pillar_of_Cybersecurity_Managing_Incidents_and_Crises_in_the_Digital_Era): Communication treated as a core capability rather than an afterthought.

- [Enhancing reliability in AI inference services: An empirical study on real production incidents](https://arxiv.org/pdf/2511.07424): An analysis of 156 high-impact production incidents with findings that generalise.

- [A Comprehensive Survey on Root Cause Analysis in (Micro) Services](https://arxiv.org/html/2408.00803v1): Root cause analysis techniques across metrics, traces, and logs.

- [Improved Root Cause Analysis Supporting Resilient Production Systems](https://www.sciencedirect.com/science/article/pii/S0278612522001273): The challenges and enablers in root cause analysis, including bias and data quality.

- [Minimizing Incident Response Time Using Quantum Computing](https://link.springer.com/article/10.1007/s11219-023-09632-6): A framing of response time as an optimisation problem at high incident volume.

- [Continual Process Improvement for ITIL Service Operations: A Lean Perspective](https://www.tandfonline.com/doi/full/10.1080/10580530.2019.1587576): A five-step improvement framework you can run after a major incident.

## Professional development tips

- Separate command from technical work explicitly, because doing both badly is the default failure
- Set a communication cadence at the start and keep it even when there is nothing new to say
- Run a broadcast channel for stakeholders so the technical channel stays usable
- Test the runbooks on a schedule, since an untested runbook is a document rather than a control
- Hand every major incident to problem management with evidence rather than a summary
- Build relationships with workplace services, infrastructure, applications and communications colleagues before you need them at two in the morning
- Debrief the people as well as the systems, since crisis work carries a real personal cost
